# R3 — Framing defensibility review of cost methodology

**Reviewer:** flint  
**Date:** 2026-04-25  
**Scope:** Can a hostile, well-informed reader poke a hole in the cost claim? Evaluated as a senior engineer who has read the audit script, has billing intuition, and is looking for a reason to dismiss the narrative.

---

## The strongest objections

### CRITICAL (would invalidate the pitch if surfaced unrebutted)

---

#### C1 — Cache writes are excluded without justification, making the headline arbitrary

The audit script's `uncached` column is defined as `(input + output)` only. Cache writes — priced at 1.25× or 2.0× the input rate — are excluded from the headline.

**Steel-man:** Cache writes are real, billable tokens that the *model processed at full rate* to produce a cached representation. The Anthropic API charges for them because they represent actual compute work. When the methodology says "uncached input + output = the model's actual generation work," that is false: cache writes *are* generation work. The `cache_creation` field in the usage object is not advisory; it is a line item on the bill. Excluding it produces a number that is lower than what the model actually did, by the methodology's own claimed standard. A reader who knows the API will immediately notice that `$2,250 + cache_write_cost ≠ $2,250`, and the document gives them no principled reason for the exclusion beyond "this matches ccusage."

**Does the methodology defend this?** No. The spec (§4.3) and design doc describe two numbers ($2,489 / $21,858) but do not explain why cache writes belong in the "full" bucket rather than the "headline" bucket. This is the single most vulnerable point in the framing because it requires the audience to accept an unexplained definitional choice that happens to reduce the headline number. Without an explicit argument ("cache writes are proportional to context window size, not to new work requested"), a hostile reader will conclude the definition was optimized to minimize the number.

**Severity:** CRITICAL. The methodology page cannot ship without explicitly addressing this.

---

#### C2 — "Matches ccusage" is appeal-to-tool, not appeal-to-billing-truth

The methodology spec says the $2,489 number "matches what `ccusage` reports." `ccusage` is a third-party community tool with no Anthropic affiliation. Its treatment of cache tokens is a convention adopted by its maintainer, not an Anthropic-endorsed definition of "model work." If Anthropic's own invoices or dashboard reported a different number, `ccusage` alignment would be irrelevant.

**Steel-man:** A skeptical reader will ask: does Anthropic's official billing dashboard show $2,489 or something else? If the answer is "we don't know — we're on Max, not API billing," then the $2,489 figure cannot be "verified by ccusage" against any ground truth; it is only internally self-consistent. The claim "matches ccusage" proves nothing about whether $2,489 is the right number — it only proves two tools agree on the same inputs with the same convention.

**Does the methodology defend this?** No. The spec says "matches ccusage" as if that is a validation step, but ccusage cannot independently validate a number it contributed to computing.

**Severity:** CRITICAL. Either drop the ccusage mention, or reframe it as "calculated using the same convention as ccusage" rather than "verified by ccusage."

---

#### C3 — The "harness artifact" claim about cache reads is load-bearing but unsupported

The methodology pivots on the claim that cache reads are a "harness artifact" — overhead generated by Claude Code re-loading context, not work the user requested. This justifies excluding them from the headline. But the spec does not prove this claim; it asserts it.

**Steel-man (three sub-objections):**

1. *Cache reads aren't free*. Anthropic charges $1.50/M for cache reads. They appear on API bills. Calling them "artifact" while simultaneously citing their cost ($12K of the $22K full price) implies you're billing Anthropic for an artifact they charge you for. The framing looks like "we want the number to be small, so anything that makes it large is redefined as overhead."

2. *If you switched harnesses, you'd lose the benefits*. The cache reads exist because Claude Code re-uses a large persistent context window across turns. That context is why agents can hold a full codebase in working memory, why they don't need to re-read files every turn, why session startup is fast. Calling the cache reads a "harness artifact" implies you could eliminate them while keeping the quality. You cannot. The cache reads *are* what you bought. Excluding them from the cost is like a taxi passenger claiming the fuel cost is a "vehicle artifact" because they could have walked.

3. *"50% reduction" is unverifiable*. If the methodology claims a different harness would reduce cache reads by ~50% (per the prompt framing), that needs to be demonstrated, not asserted. Without receipts — a concrete calculation or a second run with a different tool — it is handwaving.

**Does the methodology defend this?** Only partially. The spec acknowledges the issue in §9.2 ("some peers will read $2.5K, click through, see $22K, and conclude the README is misleading") but says the mitigation is "the methodology page leads with the headline number being the honest one." Leading with an assertion does not constitute a defense of it.

**Severity:** CRITICAL. The methodology needs either (a) a principled definition of what counts as "model work" that places cache reads outside it, or (b) honesty that this is a judgment call with a stated rationale.

### MAJOR (significant weakening of credibility)

---

#### M1 — Two-number disclosure may read as evasive, not honest

Showing $2,500 in the README and $22K on the methodology page is intended to be transparent. A hostile reader will interpret it differently: "they buried the real number two clicks away." Compare the alternatives:

- **Single number ($22K):** "We consumed $22K of compute at list rate, paying $200 via subscription." This is clean and gives the audience the most actionable comparison point. The subscription arbitrage is part of the story.
- **Single number ($200):** The cash outlay. What Cameron actually paid. This is literally true and is the number that compares to hiring costs.
- **Two numbers:** Forces the reader to adjudicate between them. An executive who bounces after the README has an incomplete picture. An engineer who reads the methodology page must evaluate the framing to decide which number to use in their mental model.

**For executives:** The most interesting comparison is total spend vs. team labor. "$200/mo vs. $50K/6-month junior" is the compelling data point. The $2,500 API-equivalent number is irrelevant to this comparison and may distract from it.

**For engineering leadership:** They understand billing. They will know cache reads exist and are charged. Showing $2,500 without immediately acknowledging the $22K makes them skeptical before they reach the methodology page.

**Defense for two numbers:** Explicit about tradeoffs — one number answers "what did the model produce" (productivity measure) and the other answers "what would this cost without the subscription" (market-rate baseline). This is genuinely useful if framed that way. But the current framing ("$2,489 is honest model work; $22K is honest list price") implies one of them is "more honest" than the other, which invites the question: which one should I actually believe?

**Recommendation:** Frame the two numbers as answering two different questions, not as "the honest number" vs. "the full number." Revise to: "Two numbers, two questions: *What did the model produce?* $2,500 (uncached input/output at API rates). *What would this cost at full API list price?* $22K (including cached context). Paid: $200/mo Claude Max."

---

#### M2 — "~$2,500" precision is off in a suspicious direction

The actual uncached number is $2,251 (per the prompt framing). The README says "~$2,500." Rounding $2,251 to $2,500 is a 11% upward round. "$2,500" to two significant figures implies the number is in the range $2,450–$2,549. The actual number is outside that range.

A hostile reader who runs the audit script themselves will get ~$2,251 and see the README says "~$2,500." They will conclude:
- Either the README number is stale (audit was run before final sessions), or
- The number was rounded up for effect.

Neither conclusion is flattering. "$2,500" is also not a natural rounding of $2,251 — the natural rounds are "$2,200," "$2,300," or "$2,000–$2,500 range."

**Recommendation:** Use "~$2,300" or "~$2,250" as the README figure, or report as "~$2,000–$2,500" to honestly indicate precision. Update `COST_METHODOLOGY.md` to the corrected number ($2,251) rather than the original spec's $2,489.

---

#### M3 — "Anyone can reproduce" overstates what the script actually enables

The methodology page (per spec §6.4) says "reader can verify on their own `~/.claude/projects/*/`." This is subtly misleading. The reproduction instruction lets the reader verify *their own* cost, not *this project's* cost. The specific transcript data at `~/.claude/projects/-home-administrator-Code-geographica/` is private to Cameron. An outside auditor cannot run the script against Cameron's data.

What the methodology actually provides: a method Cameron can use to re-verify his own numbers at any point in the future. That is valuable and honest, but it is not "reproducible" in the scientific sense — no independent party can audit the $2,251 figure from first principles without access to the private transcript directory.

**Does this matter?** Probably not to most readers. But a skeptical engineer will notice the distinction between "you can reproduce this" and "I can reproduce this." The wording should say "Cameron can re-verify; you can audit your own costs using the same method" — not imply third-party verifiability.

---

#### M4 — The "actually paid" claim likely undersells the real cost

The methodology says "What was actually paid: ~$200/mo Claude Max subscription." Possible gaps:

1. **Codex CLI / ChatGPT Plus:** The CLAUDE.md and adversarial review workflow explicitly use `npx --yes @openai/codex` for R5/R6 review rounds. Codex CLI in "ChatGPT mode" requires a ChatGPT Plus subscription (~$20/mo) or API credits. If Cameron has ChatGPT Plus, that is another ~$20/mo that contributed to inference and should be in the cost picture.

2. **API credits for non-Max usage:** If any sessions used API keys instead of the Max subscription (e.g., early sessions, testing, MCP-server mode), those would be direct charges, not subscription-covered. The audit script has no way to distinguish these.

3. **Hailo NPU:** The CLAUDE.md mentions a Hailo 10H NPU for "Phase 2, AI voice commands." If any inference ran on the NPU, it is outside both subscription and API cost accounting.

4. **Hardware:** The spec explicitly excludes hardware costs (decision §4.2: "hardware dollar figures are omitted — they age poorly"). An executive will mentally include hardware. A Pi 5 with 16 GB RAM + SSD is ~$150–$200. Excluding it is defensible for the "inference cost" frame but should be explicitly called out: "hardware costs (~$150 for a Pi 5 + SSD) are excluded; inference only."

**Severity:** MAJOR. Item 1 (Codex/ChatGPT Plus) is the most credible gap. If it applies, the "actually paid" figure should be "~$220/mo" or similar.

---

#### M5 — The pitch does not invite the comparison that makes it compelling

"$2,500 to ship a GIS stack in 19 days" is a remarkable claim. But the methodology page does not help the reader understand what to compare it to. A senior engineer or executive will mentally compare:

- **Junior engineer labor:** A 6-month project at $100K/yr = ~$50K labor alone, before benefits (1.3–1.5× = $65–75K total cost). The Claude Max subscription is 0.3% of that figure. This comparison makes the pitch extremely strong.
- **Off-the-shelf GIS:** ArcGIS license alone is $1,500–$20,000/yr. ESRI enterprise is higher. This comparison is favorable.
- **Cursor/Copilot alternative:** A senior engineer + Cursor for 6 months = ~$65K labor + ~$120 Cursor = still $65K.

None of these comparisons appear in the proposed methodology page. Without them, the reader does the math themselves — and may anchor on the wrong reference class (e.g., "that's a lot for a side project" rather than "that's 0.3% of equivalent team labor").

**Recommendation:** Add a "Context" subsection to the methodology page that does this comparison explicitly, or at minimum points to it in `PROCESS.md`.

### MINOR (nits, framing improvements)

---

#### m1 — "19 days" needs a defined start and end date

The pitch says "19 days." An auditor will ask: Day 1 to Day 19 of what? Does the transcript data align to that window? The audit script processes *all* transcripts in `~/.claude/projects/<slug>/`, with no date filter. If any pre-19-day exploratory sessions exist in that directory (e.g., architecture sketches, initial setup before the clock started), they are included in the $2,251. If any post-Day-19 sessions exist (ongoing bug fixes, post-launch maintenance), they are also included.

The methodology page should state the exact window (e.g., "2026-04-06 through 2026-04-24") and confirm whether the transcript data is scoped to that window or is all-time.

---

#### m2 — Cache write pricing in the script does not match current Anthropic rates

The audit script prices `cache_w_5m` at 1.25× input rate and `cache_w_1h` at 2.0× input rate. These are specific TTL variants (5-minute ephemeral, 1-hour ephemeral). The current Anthropic API also has persistent (24h+) cache writes priced at 1.25× for Sonnet/Haiku families. If the transcripts contain any `cache_creation` tokens outside the `ephemeral_5m` / `ephemeral_1h` keys, they will be silently dropped (the script only reads those two keys from `cache_creation`). The methodology should note this assumption or verify it is exhaustive.

---

#### m3 — "Proportional rates for Sonnet/Haiku" is vague in the README callout

The README says "API-equivalent model output = (uncached input × $15/M) + (output × $75/M) for Opus, plus proportional rates for Sonnet/Haiku." A reader cannot reconstruct the Sonnet rate from "proportional." The methodology page should spell out all three tiers (Opus: $15/$75, Sonnet: $3/$15, Haiku: $1/$5) to make the disclosure complete. The audit script has these rates; the doc should match.

---

#### m4 — The README uses "API-equivalent" as a term of art without defining it

"API-equivalent model output" is jargon invented for this methodology. A reader who knows Anthropic's pricing may assume "API-equivalent" means "at API list rate" (i.e., full price including cache), which would land at $22K, not $2,500. The term needs to be defined in the README callout or replaced with plain language: "uncached input and output tokens, priced at API list rates."

---

#### m5 — "$21,858" vs. "~$19,800" — which is in the methodology?

The prompt framing notes the corrected numbers are "~$2,250 uncached / ~$19,800 full" but the spec's original numbers are "$2,489 / $21,858." The methodology page needs to use the corrected figures and note when/why the correction was made, or readers who saw an earlier draft will see a discrepancy.

## What the methodology page already addresses well

1. **Two-number disclosure is structurally sound.** Showing both numbers is better than omitting one. The intent to be transparent about the full list price is correct and credible.

2. **Cache reads are legitimately distinguishable from other token categories.** The claim that 8.1 B cache read tokens represent context reloading rather than new generation work is defensible *if argued*. The intuition is correct; the document just needs to make the argument rather than assert the conclusion.

3. **Audit script is a genuine artifact.** Shipping `scripts/audit_inference_cost.py` alongside the claim is more credible than a bare assertion. It shows the methodology is mechanistic, not post-hoc.

4. **Acknowledging the $22K is not a lie of omission.** Spec §9.2 names the risk explicitly ("some peers will read $2.5K, click through, see $22K, and conclude the README is misleading"). This self-awareness is the right starting point; it just needs to translate into better copy on the methodology page itself.

5. **Hardware exclusion is defensible if labeled.** "Inference cost only" is a reasonable scope for a cost methodology; hardware is genuinely separate. The document just needs to say so explicitly.

## Recommended copy / counter-frames

### For C1 (cache write exclusion)

Add this to the methodology page under "Headline number":

> **Why exclude cache writes?** Cache writes price the act of *creating* a cached representation, not of generating new content. They are proportional to context size, not to the work requested in each turn. A session that re-reads the same 100K-token codebase 50 times accumulates the same cache-write cost regardless of whether it produces one line or 10,000 lines of output. Including them in a "model work" metric would conflate context management overhead with productive generation. They are real charges — included in the full list price — but they answer a different question than "how much did the model generate?"

### For C2 (ccusage framing)

Replace "matches ccusage" with:

> "This definition — uncached input plus output — is the same convention used by the community tool `ccusage`. It is not an Anthropic-endorsed definition; it is a deliberate choice to measure productive generation separately from cache overhead. The audit script ships with this repository so any reader can inspect and challenge the convention."

### For C3 (cache reads as harness artifact)

Add explicit language:

> **Cache reads:** Claude Code reloads a large persistent context (~336K tokens per turn) to maintain agent memory across a session. This accumulates cache read charges ($1.50/M) that scale with session length and context size, not with the complexity of the work requested. A Claude Code session doing trivial edits accumulates the same cache-read cost as one writing complex algorithms, because the context window is the same. These are real Anthropic charges — hence their inclusion in the full list price — but they measure harness behavior, not generation work. Readers who consider them part of the cost should use the $19,800 figure.

### For M1 (two-number framing)

Revise the methodology page "Why two numbers" section:

> **Two numbers, two questions.** "$2,300" answers: *What did the model actually generate?* (uncached tokens, the measure of productive output). "$19,800" answers: *What would this cost at full API list price, no subscription?* (every charged token category at Anthropic list rates). They are both correct; they answer different questions. Use $2,300 to compare model productivity across projects; use $19,800 to assess subscription value. Neither is the "real" cost to the exclusion of the other.

### For M2 (rounding)

Change README from "~$2,500" to "~$2,300" (or "~$2,250"). Update the methodology page headline from $2,489 to $2,251 (or whatever the re-run produces). Add: "Last audited: 2026-04-25. Numbers increase as the project continues."

### For M3 (reproducibility honesty)

Change "reader can verify" to:

> "Cameron can re-verify these numbers at any time by re-running the audit script against the private transcript directory. Readers can verify their own Claude Code project costs using the same method; the transcript data is private per-user."

### For M5 (invite the comparison)

Add a "Context" block to the methodology page or to `PROCESS.md`:

> **Reference comparisons.** An equivalent feature set built by a senior engineer over 6 months: ~$65,000–$75,000 loaded labor cost. ArcGIS license for the equivalent capability: $5,000–$20,000/yr, plus integration labor. A Claude Max subscription for the development period: ~$200. The inference cost of $2,300 (API-equivalent) or $19,800 (full list) represents productivity leverage of roughly 30–40× against baseline labor cost, not an apples-to-apples replacement.

## Recommendation

**Revise framing per recommendations — do not ship the methodology page as currently specced.**

The structural decisions (two-number disclosure, separating cache reads from headline, shipping the audit script) are correct. But three issues would be raised immediately by a well-informed reader and are not pre-empted by the current spec:

1. Cache write exclusion is unexplained. A reader applying the methodology's own stated standard ("actual generation work") will expect cache writes to be included in the headline.
2. The ccusage citation validates nothing without a principled definition backing it.
3. "Cache reads are a harness artifact" is asserted, not argued.

All three are fixable with one to three paragraphs of additional reasoning in `COST_METHODOLOGY.md`. The revisions above provide draft language for each. The current draft is 80% of the way there — it just needs the three arguments made explicit rather than implied.

The README callout is clean and defensible once the methodology page is strengthened. The two-number structure, the audit script artifact, and the honest disclosure of the $19,800 figure are all genuine assets to the pitch. The work is in the fine print, not the headline.
