# Multipass bug hunt — pipeline sticky error state
**Date:** 2026-04-24
**Agent:** manzanita
**Scope:** `services/search/main.py` (`/admin/pipeline/{start,status,cancel}`, helpers L1138–L1266, L72 lock), `frontend/config/index.html` (startPipeline L1328, renderNoaaBody L1400, Custom-area Start handler L1820, updatePipelineButtons L2857, fetchAll L3172, renderGenericProgress L2658), `scripts/acquire_imagery.py` (multi-state guard L2229–L2244, update_progress L461–L573, _atomic_write_json L451).

Passes performed: 1 (contract), 2 (cross-sibling), 3 (failure modes), 4 (concurrency), 5 (error propagation).

## Pass 1 — Contract violations

- **Finding 1.1 — `_is_pipeline_container_running` silently treats all Docker API errors as "not running":** `services/search/main.py:1181-1187`. The docstring claims it returns True when any pipeline container is running (admin or CLI flavors), but the bare `except Exception: return False` swallows Docker-socket disconnects, timeouts, or permission errors. A flapping Docker socket looks indistinguishable from "no pipeline running", so /start's 409 gate at L1396 can admit a second pipeline while the first is still running. **Blast radius:** duplicate pipeline launches that race on the same state file and MBTiles.

- **Finding 1.2 — `_noaa_peak_and_snapshot` conflates three distinct outcomes into `([], 0.0, None)`:** `services/search/main.py:1219-1247`. The docstring promises "([], 0.0, None) when the catalog isn't loadable", but the function also returns that sentinel when (a) the user's `state` is unknown or uncataloged (L1234), (b) `body.bbox` is falsy (L1241), and (c) bbox intersects only uncataloged states (L1246). Caller /start L1348 treats all three as "no_catalog" with the same error message ("POST to /admin/pipeline/noaa/refresh first, or pick a bbox that intersects a cataloged state"), which is actively misleading for cases (a) and (c). **Blast radius:** user debugging an uncataloged-state bbox is told to refresh the catalog, sends another refresh, comes back to the same failure.

- **Finding 1.3 — /start comment at L1336-1340 claims the catalog snapshot is stable across the pipeline-lock window, but that invariant is silently broken for states with status "error":** `services/search/main.py:1336-1340`. The "pipeline-not-running invariant enforced by /refresh and /rollback" hinges on `_is_pipeline_container_running` being honest. An exited container with error state is not a running container, so /refresh and /rollback CAN execute between the /start-estimate view and the /start click, swapping the catalog symlink. The snapshot_path recorded at L1342 then does not match what the pipeline container will pin at startup (see `scripts/acquire_imagery.py:2200-2216`). **Blast radius:** silent disagreement between estimate UI and the pipeline container's actual scope; subtle data-corruption vector if a rollback races Start.

- **Finding 1.4 — /status promises "no auth required" at L1633, but the reconciler at L1678-1761 performs privileged writes (state file overwrite, Docker container log capture, TileServer restart) with no authentication:** `services/search/main.py:1631-1764`. The docstring says "Get current pipeline job status (no auth required)". But the handler performs side effects: at L1758 it rewrites the state file via tmp+rename, at L1746 it restarts a TileServer container, at L1736 it issues a `PRAGMA wal_checkpoint(TRUNCATE)` on the MBTiles. A read endpoint that restarts containers and checkpoints SQLite is not a read endpoint. **Blast radius:** any unauth caller that can reach /status can induce TileServer restarts and state-file rewrites; DoS surface via poll-spamming.

- **Finding 1.5 — `_state_file_for_type` silently falls through to the imagery path for unknown types:** `services/search/main.py:1138-1150`. The function has no explicit error for unrecognized `pipeline_type`; typos like `"naiip"` return `.pipeline-state.json`, which collides with the imagery state. The caller is /admin/pipeline/status L1632 which does validate via Query enum. But /admin/pipeline/cancel at L1789-1796 iterates a hard-coded list — if a new pipeline type is added to `_state_file_for_type` without being added to that list, cancel silently skips it. **Blast radius:** future-proofing defect; not today's bug.

## Pass 2 — Cross-sibling pattern deviations

- **Finding 2.1 — /start's state-file write (L1617) does NOT use the atomic tmp+rename pattern that every sibling write-site uses:** `services/search/main.py:1617` (`state_file.write_text(...)`) vs. `services/search/main.py:1758-1759` (`/status` reconciler — tmp+rename), `services/search/main.py:1802-1804` (`/cancel` — tmp+rename), `scripts/acquire_imagery.py:451-458` (`_atomic_write_json` — tmp+fsync+rename), `scripts/acquire_imagery.py:573` (all pipeline progress writes). The non-atomic write creates a window in which a concurrent /status read sees an empty/truncated file and falls through the `json.JSONDecodeError` handler at L1642 to `{"status": "unknown", ...}`. Every other writer in the project understood the atomicity requirement; /start is the sole outlier. **Blast radius:** transient UI flicker showing "status: unknown" after Start; more seriously, the /status reconciler reading during that window sees the old "error" state (if truncation hasn't happened yet) or "unknown" (if it has), and may writeback stale content at L1758.

- **Finding 2.2 — /cancel only flips state when `status == "running"`; it does NOT clean up terminal error states:** `services/search/main.py:1800`. None of the sibling operations on the state machine — /start, /status, /cancel — offer a way to reset `status: "error"` to idle. Compare with /admin/pipeline/noaa/refresh which has an explicit /reset endpoint (referenced by `CANCEL_TIMEOUT_SEC` L85 comment). The main pipeline state machine has no equivalent — once you're in "error", you can only leave by a successful Start. **Blast radius:** this is the reported sticky-error bug. If /start fails for any reason (image missing, catalog missing, multi-state bbox, 409-disk, 500-Docker), the error state from the previous crash remains; the user's UI keeps showing the old error, with no user-visible control to clear it.

- **Finding 2.3 — /start performs a multi-state check NOWHERE, though the pipeline container crashes with a deterministic error message ("multi-state dispatch is not yet implemented") the server is perfectly equipped to detect:** `services/search/main.py:1341-1385` vs. `scripts/acquire_imagery.py:2229-2244`. The server already calls `states_intersecting(body.bbox)` inside `_noaa_peak_and_snapshot` at L1242. Adding a single guard for `len(states_list) > 1` would reject multi-state bboxes with a proper 409 before dispatch. Siblings `is_sentinel`, `is_naip`, `is_m2m` all validate their pre-requisites up-front; NOAA defers this check to the container. **Blast radius:** every multi-state NOAA submission writes an error-state pipeline-state.json that only a subsequent successful Start can clear (see 2.2).

- **Finding 2.4 — The /start NOAA peak-disk gate (L1373-1385) runs BEFORE the pipeline lock but /start's other "already running" checks (L1396-1407) run AFTER the lock:** `services/search/main.py:1336-1387`. Pre-lock checks can miss a concurrent /start that started a pipeline microseconds before. Every sibling guard (catalog missing, missing-unack, disk) runs pre-lock, yet only the duplicate-pipeline guard runs inside the lock. This asymmetry means a concurrent /start that loses the lock race can still pass the pre-lock checks, then correctly 409 on the post-lock check — but by then disk/catalog state may have changed. Not a sticky-error cause but a symptom of inconsistent gating. **Blast radius:** subtle; two near-simultaneous /start calls can race the disk check.

- **Finding 2.5 — NAIP Start at L1472-1481 and Sentinel Start at L1465-1471 do NOT call `update_progress` equivalents on their own state files; instead they rely on /start writing the initial running state and the script writing subsequent states.** The bug: /start writes to `_state_file_for_type(body.type)` (correct per-type file, L1400). But the pipeline SCRIPT (`scripts/acquire_imagery.py`) always writes to `Path(output_path).parent / ".pipeline-state.json"` (L483, L343, L423, L805) — which for NAIP would be `/data/.pipeline-state.json`, NOT `/data/.naip-state.json`. **This means NAIP pipelines write their running-state progress to the imagery state file, stomping on any in-flight imagery progress and losing NAIP progress.** Same for Sentinel (script writes to `.pipeline-state.json`, but /start writes to `.sentinel-state.json`). **Blast radius:** cross-contamination of state between pipeline types; NAIP/Sentinel progress invisible to /status?type=naip (which reads `.naip-state.json`).

## Pass 3 — Failure mode reasoning

- **Finding 3.1 — /start's stale-container cleanup at L1582-1587 silently ignores all failure modes except NotFound:** `services/search/main.py:1582-1587`. The bare `except Exception: pass` catches the docker-py NotFound (OK — no old container to remove), but also catches APIError (old container exists but can't be removed due to filesystem lock, overlayfs issue, etc.). In the APIError case, the subsequent `containers.run(name="geographica-pipeline", ...)` at L1590 raises `409 Conflict - container name already in use`, which is caught by L1621 and returned as HTTP 500. The state file was NOT rewritten because the write at L1617 never executes. **Blast radius:** on this failure path, the old error state persists in the state file, the user sees an HTTP 500 alert, and polling shows the old error indefinitely — matching the reported sticky-error symptom.

- **Finding 3.2 — Multi-state pipeline crash path (L2229-2244 in acquire_imagery.py) writes status="error" but does NOT remove the container, nor does /start check container.status on the next attempt:** `scripts/acquire_imagery.py:2240-2244` calls `sys.exit(1)`, the container exits, Docker keeps it in "exited" state (because `remove=False` was passed at main.py L1595). On the next /start: L1584 tries to remove it, L1585 force-removes. If that succeeds, fine. If anything goes wrong (3.1 path), we're stuck with the old container AND the old error state. **Blast radius:** cascade of 3.1.

- **Finding 3.3 — `_noaa_peak_and_snapshot` return-path audit:** Traces through all return sites:
  1. `_load_noaa_catalog` returns (None, None): L1220-1221 → `([], 0.0, None)` → caller 409s.
  2. `body.state` set but USPS unknown and slug not in entries: L1233-1235 → `([], 0.0, None)` → caller 409s ("pick a bbox that intersects a cataloged state", which is misleading for a state=arizona request).
  3. `body.state` None AND `body.bbox` falsy: L1240-1241 → `([], 0.0, None)` → caller 409s. Valid on the Whole-state tab (has state but no bbox), but caller code already set state. Valid on Custom-area (has bbox), but code already set bbox. Dead-path in practice.
  4. Bbox intersects, but no cataloged states in the intersection: L1246-1247 → `([], 0.0, None)` → caller 409s. **Valid single-state bbox where that single state is uncataloged → user is told "catalog not loaded" — wrong message.**
  5. Success: returns (missing_list, peak, str(snapshot_path)). **Note:** `missing` can be `[]` even when bbox intersects states, if all those intersecting states are cataloged. Caller at L1361 skips the missing-unack 409 correctly.
  
  **Blast radius:** user-visible misleading errors; no sticky state directly, but contributes to "I can't make this work" frustration.

- **Finding 3.4 — State file JSON parse failure at L1406 masks everything:** `services/search/main.py:1401-1407`. `try: state_data = json.loads(state_file.read_text()); if state_data.get("status") == "running" and _is_pipeline_container_running(client): raise HTTPException(409, ...); except json.JSONDecodeError: pass`. If the file is mid-rewrite (recall 2.1 — /start's non-atomic write) AND a second concurrent /start races, the reader sees empty/truncated JSON, hits `pass`, skips the 409 check, and proceeds to start a SECOND pipeline. **Blast radius:** two pipelines racing, stepping on each other's state files and the MBTiles.

- **Finding 3.5 — Container starts but fails before writing any progress; state retains `status: "running"` indefinitely:** Scenario: /start writes "running" at L1617. Container boots, Python imports fail (e.g., missing module after a recent deploy), container exits with non-zero code before `update_progress` is called. `_is_pipeline_container_running` returns False. /status reconciler at L1671 detects `status="running" AND not container_running` → is_crash_path=True. Logs tail grabbed at L1697. No success markers match → `new_status = "interrupted"` at L1713. State flips to "interrupted". **OK, covered.** But what if the logs tail capture at L1697 fails and `state_data["last_logs"]` is never set? L1705 reads `state_data.get("last_logs") or ""` → empty string → no success markers → interrupted. Covered. **BUT**: what if the container is in "created" state (pre-running) for >10s because Docker is slow? `_is_pipeline_container_running` checks `c.status == "running"` only (L1185) — "created" returns False. First /status poll within the 10s interval marks the pipeline as interrupted, stomping the "running" state /start just wrote. **Blast radius:** false "interrupted" verdict during slow Docker startups; state file diverges from reality.

- **Finding 3.6 — /status reconciler writeback at L1756-1761 clobbers fresh /start state:** When (3.5) fires: /status reads state at L1641, decides is_crash_path=True, builds updated state_data, writes it at L1758-1759. If /start raced meanwhile and wrote `status: "running"` with new container_id at L1617, and /status had already read the old state (pre-Start), the reconciler writeback overwrites /start's update with the stale "interrupted" content. **The pipeline actually runs** (docker container is alive), but the state file says "interrupted" — a subsequent /status sees state="interrupted" and is NOT on is_crash_path, so no reconcile; the real container's update_progress eventually writes "running" and heals this. **Blast radius:** transient UI confusion; resolves in ~10s once the real container starts writing progress.

## Pass 4 — Concurrency reasoning

- **Finding 4.1 — /status acquires NO lock but performs state-file writes at L1758:** `services/search/main.py:1631-1764`. /status writes can race with:
  - /start's non-atomic write at L1617 (open-truncate-write is NOT atomic).
  - The pipeline container's `_atomic_write_json` at `scripts/acquire_imagery.py:458` (atomic; but without a shared lock, the reconciler's state_data was computed from a read that could be pre- or post-atomic-write).
  - /cancel's atomic write at L1802-1804 (same caveat).
  The writebacks at L1758-1761 use tmp+rename but the state_data they write was built from a stale read. **Classic TOCTOU.** Example concrete failure: pipeline writes "completed", /status reads "completed", decides is_clean_terminal=True, container_running=False, starts restart of TileServer. Meanwhile pipeline writes `tileserver_restarted_at` itself? (It doesn't — only main.py writes that.) Meanwhile /start races and writes "running" for a new run. /status's writeback stamps `tileserver_restarted_at` + keeps status="completed" into the state file, clobbering the fresh "running" write. **User sees pipeline "completed" forever even though a new one is running.** **Blast radius:** sticky-completed; another flavor of the reported bug, with a different trigger.

- **Finding 4.2 — `state_file.write_text(json.dumps(...))` at L1617 is not atomic but shares the state file with atomic writers:** `services/search/main.py:1617`. Non-atomic writer + atomic readers + atomic writers in the same namespace. Windows are short (a single write_text for a ~500-byte dict) but non-zero. **Blast radius:** per 3.4, a racing reader can see empty JSON and silently `pass` the 409 check, letting a second pipeline start.

- **Finding 4.3 — `_pipeline_lock` is a module-level asyncio.Lock, per-worker:** `services/search/main.py:72`. The comment treats it as a global invariant ("pipeline-not-running invariant"). In a multi-worker deployment (uvicorn --workers >1), each worker has its own lock. Two concurrent /start requests routed to different workers both pass the lock check and then race on `containers.run(name="geographica-pipeline", ...)` — Docker will 409 the loser, caught at L1621 as HTTP 500. OK for the container layer, but the L1617 state-file writes will stomp each other. **Blast radius:** in single-worker deployment (Geographica's current config) this is fine; in any future scale-out it's a latent bug.

- **Finding 4.4 — /start's pre-lock NOAA checks (L1341-1385) use catalog snapshot via `_noaa_peak_and_snapshot`, which resolves the symlink at L1219 via `_load_noaa_catalog`. The value used to write state (`snapshot_path`) is computed pre-lock; nothing enforces that /refresh can't swap the symlink BEFORE the pipeline container starts AND reads the pinned snapshot (`pin_catalog_snapshot` at L2196 of acquire_imagery.py):** `services/search/main.py:1336-1342, 1387-1600`. The comment at L1336-1340 asserts "pipeline-not-running invariant enforced by /refresh and /rollback means the catalog snapshot is stable once we enter the lock" — but /refresh checks `_is_pipeline_container_running`, which returns False for an EXITED container (error state). A new /refresh can run between old-pipeline-error and new-/start, changing the symlink. `_noaa_peak_and_snapshot` resolves pre-lock; by the time `containers.run` at L1590 fires, the symlink may have been swapped again. **Blast radius:** subtle; pipeline processes a different snapshot than the /start estimate saw. Not the sticky-error cause but a stated invariant that's false.

- **Finding 4.5 — /cancel races with /start on the state-file overwrite:** `services/search/main.py:1787-1806` vs. `services/search/main.py:1602-1617`. Both acquire `_pipeline_lock` so serialized within one worker. But /cancel only mutates if `existing.get("status") == "running"` (L1800). If /start is still executing (held the lock, but between containers.run and state write), /cancel queued on the lock won't see "running" yet because the state file still holds OLD content. After /start releases lock, /cancel acquires it, reads new "running" state, flips to "cancelling", and SIGTERMs the just-started container. Probably safe in practice (SIGTERM is clean), but the semantics are "cancel a barely-started pipeline". **Blast radius:** benign but visible: user clicks Start twice quickly (once by impatience, once perceived as first-click-ignored), second click goes to Cancel by accident, and the pipeline dies immediately after starting.

## Pass 5 — Error propagation

- **Finding 5.1 — User-facing alert for /start 500 errors exposes raw exception detail:** `services/search/main.py:1621-1622` (`HTTPException(500, detail=f"Failed to start pipeline: {e}")`) → `frontend/config/index.html:1338` (`alert(d.detail || 'Start failed')`). A Docker `APIError: 409 Client Error...` becomes `alert("Failed to start pipeline: 409 Client Error: Conflict (\"Conflict. The container name '/geographica-pipeline' is already in use...\")`. **No recovery guidance, no "click here to reset".** User Googles, gives up, files a bug. **Blast radius:** UX; contributes to "sticky" perception because user doesn't know what to do.

- **Finding 5.2 — The multi-state error message at L2236-2240 tells the user to "Pick a single state from the 'Whole state' tab, or narrow the bbox" — but the UI provides no easy way to discover which 3 states intersected.** `scripts/acquire_imagery.py:2235-2240`. The message DOES include the USPS codes ("bbox intersects 3 states (AZ, CA, NV)"). The UI renders this via `completedEl.textContent = (sourceLabel || 'Download') + ' failed' + (ago ? ' ' + ago : '') + (d.error ? ' — ' + d.error : '')` at frontend L2743. So the user DOES see "AZ, CA, NV". OK. **Minor:** after user re-draws to NV only, there's no way to VERIFY it's single-state without clicking Estimate (which is optional). If the user skips Estimate and clicks Start, the multi-state error can repeat if their bbox still crosses a border by a hair.

- **Finding 5.3 — `except (json.JSONDecodeError, OSError):` at L1642-1643 masks permission/disk errors as "Could not read state file":** `services/search/main.py:1639-1643`. If the state file has perm-denied or the disk is full (affecting both read and write), the status endpoint returns `{"status": "unknown", "error": "Could not read state file"}`. Frontend renderGenericProgress hits the else branch at L2838, hides everything. **The real error (permission, disk-full) is not surfaced to the user.** **Blast radius:** user sees blank card, no error, not running — infinite confusion. Applies equally to sticky-error recovery: if the state file ever becomes corrupt, the user has no way to know.

- **Finding 5.4 — /status reconciler's logs-capture path silently drops all exceptions at L1699-1700:** `services/search/main.py:1691-1700`. `except Exception: pass`. If log capture fails (container gone between existence check and logs() call), state_data["last_logs"] is never set, and the "completed vs interrupted" decision at L1702-1713 relies on empty-string logs → always "interrupted". A clean completion that ends milliseconds before /status polls looks like an interruption. **Blast radius:** false "interrupted" verdict for clean completions where the container was reaped quickly.

- **Finding 5.5 — /cancel swallows all Docker errors at L1823-1824 and returns `{"status": "cancelling"}` unconditionally:** `services/search/main.py:1812-1828`. Even if the container stop failed, the user sees "cancelling". Eventually the container either stops on its own or keeps running. /status reconciles based on `container_running` — so the state does eventually self-heal — but during the window, the user is told the cancel succeeded when it may not have. **Blast radius:** user thinks cancel worked, navigates away, pipeline keeps running.

- **Finding 5.6 — Sticky-error-state core cause: no server-side reset path.** The error state (written by pipeline at L2242 acquire_imagery.py) has no natural expiration. /start only rewrites state on successful Docker container launch (L1617, inside try block); if Start fails for any reason, the error persists. /cancel only flips `status == "running"` (L1800). /status reconciler only writes back on is_crash_path or is_clean_terminal; neither triggers for status="error". There's no /reset or /clear endpoint for the main pipeline state (only for NOAA refresh state, via `CANCEL_TIMEOUT_SEC` at L85 referencing a /reset path for refresh). **Blast radius:** this is the reported sticky bug. No code path the user can trigger via UI will clear the error state, except a successful Start — which requires all pre-checks to pass AND all Docker calls to succeed.

## Summary

### Bugs confirmed

**Critical (directly explain reported stickiness):**
- **B1 (Finding 2.2 / 5.6): No path clears `status: "error"`.** No code path in /status, /cancel, or the frontend can dismiss or reset a pipeline error state. The only clear path is a successful /start, which means any /start failure (image conflict, multi-state bbox, insufficient disk, Docker hiccup, stale container) leaves the user permanently stuck on the previous error with no UI affordance to recover. **Location:** `services/search/main.py:1787-1828` (/cancel doesn't clear errors); `services/search/main.py:1678-1714` (/status reconciler doesn't clear errors); no /reset endpoint exists.

- **B2 (Finding 2.3): /start does not pre-validate single-state-only for NOAA mode.** The pipeline container crashes with a deterministic "multi-state dispatch is not yet implemented" error that the server has all the information to detect (via `states_intersecting` already called inside `_noaa_peak_and_snapshot`). Every multi-state submission → pipeline crash → error state → trapped by B1. **Location:** `services/search/main.py:1336-1385` lacks the guard; `scripts/acquire_imagery.py:2229-2244` is where the container crashes.

- **B3 (Finding 3.1): /start's stale-container cleanup silently swallows removal errors.** Bare `except Exception: pass` at `services/search/main.py:1586-1587` masks Docker APIErrors. A failed removal leaves the exited container in place; the subsequent `containers.run(name="geographica-pipeline", ...)` raises a 409, caught as HTTP 500. The state file is NOT rewritten because the write at L1617 is past the crash point. User sees alert("Failed to start pipeline: ..."); state still says "error". **Blast radius** overlaps with B1 — the user is stuck.

**Significant:**
- **B4 (Finding 2.5): NAIP and Sentinel pipeline scripts write progress to `.pipeline-state.json`, not their own per-type state file.** `scripts/acquire_imagery.py:483` hardcodes `state_path = Path(output_path).parent / ".pipeline-state.json"`. But /start at `services/search/main.py:1400` and /status at L1637 route per-type via `_state_file_for_type`. **NAIP and Sentinel running state is invisible to the frontend poll** (which queries `?type=naip` → reads `.naip-state.json` → empty), and **stomps on imagery state** (writing running/progress to `.pipeline-state.json` when imagery may have a real error state there).

- **B5 (Finding 2.1 / 4.2 / 3.4): /start's state-file write at L1617 is not atomic, yet every other writer in the project uses tmp+rename.** Creates a window in which concurrent /status reads see truncated/empty JSON, fall through `json.JSONDecodeError: pass` at L1406, and skip the duplicate-pipeline 409 check. Two concurrent /start calls can bypass the gate and launch two pipelines.

- **B6 (Finding 3.5): False "interrupted" verdict when Docker is slow to transition a container to `running` status.** `_is_pipeline_container_running` at L1185 requires `c.status == "running"` — a "created" container (Docker still setting up namespaces/mounts) returns False. /status reconciler at L1671 sees "running" state + no container → is_crash_path=True → stamps "interrupted" over the fresh /start state at L1758. Self-heals once the container's first `update_progress` fires, but the user sees a transient "interrupted" flash.

- **B7 (Finding 4.1): /status performs state-file writebacks without holding `_pipeline_lock`.** Classic TOCTOU. Concrete failure: user just successfully started a new run; /status (polling concurrently) reads pre-/start state ("completed"), decides is_clean_terminal=True, stamps `tileserver_restarted_at`, writes "completed" back — clobbering the fresh "running" state that /start wrote. User sees pipeline "completed" forever while the actual pipeline runs to success with no UI update.

- **B8 (Finding 1.4): /status performs privileged side effects (state-file write, TileServer restart, WAL checkpoint) with no authentication,** despite its docstring claiming "no auth required" and its routing outside the `require_config_source` dependency. Any caller on the public network can induce TileServer restarts by polling /status.

**Minor:**
- **B9 (Finding 1.1): `_is_pipeline_container_running` returns False for any Docker API error** — indistinguishable from "no pipeline running". Could allow duplicate launches on socket flap.
- **B10 (Finding 1.2 / 3.3): `_noaa_peak_and_snapshot` returns the same sentinel `([], 0.0, None)` for four distinct outcomes,** producing misleading user-facing error text at /start L1348 for cases other than "catalog absent".
- **B11 (Finding 5.4): Log-capture exception at L1699 falls through to always-"interrupted" verdict** for clean-completion-with-fast-reap races.
- **B12 (Finding 5.3): State-file read errors at L1642-1643 return `"status": "unknown"`** without surfacing permissions/disk-full to the user; frontend renders nothing.
- **B13 (Finding 4.4): /start's "catalog snapshot is stable" invariant at L1336-1340 is false across error states** — /refresh treats exited containers as idle and can swap the symlink between estimate and /start.
- **B14 (Finding 5.5): /cancel returns `{"status": "cancelling"}` even when Docker stop failed** (all exceptions swallowed at L1823-1824).
- **B15 (Finding 5.1): Raw Docker exception strings leak to user alert** at frontend L1338 with no recovery guidance.

### Unconfirmed suspicions

- **S1:** `_is_pipeline_container_running` filter `{"name": "geographica-pipeline"}` — I did not verify docker-py's substring vs. exact-match semantics for name filters. If it's exact-match, the docstring claim of catching "geographica-pipeline-run-*" CLI containers is false. Worth verifying against docker-py's docs.
- **S2:** The `container_id` written at L1614 is never cross-checked by /status. If a stale container with the same name exists and a new one was started, but the state file records the old container_id, log-capture at L1693-1697 picks the wrong container's logs. `containers.list(all=True, filters={"name": "geographica-pipeline"})` returns by name filter; `containers[0]` is nondeterministic ordering.
- **S3:** Frontend's `_anyPipelineRunning` is derived from 5 per-type flags updated in 5 independent promise chains at L3181-3221. If one poll is slow/fails, the flag can be stale, enabling/disabling buttons incorrectly. Not sticky-error per se, but a UX gap in multi-pipeline state coordination.

## Design concerns

- The pipeline state machine has `running`, `cancelling`, `cancelled`, `interrupted`, `completed`, `completed_partial`, `partial_failed`, `error`, `unknown` — NINE states, most lacking explicit transitions. The state graph is implicit, scattered across /start, /cancel, /status reconciler, and every `update_progress` call. A single state-machine module with explicit transitions + a `/reset` endpoint that only permits `error → idle` would close B1, B3, and most of the "sticky" failure modes.

- Two writers (main.py and acquire_imagery.py) share `.pipeline-state.json` with no shared locking protocol. The pipeline script uses atomic writes; main.py mostly does but L1617 is an exception. The split ownership — "API writes initial state, script writes progress+terminal, API reconciles crash" — is fragile. Moving ALL writes into the script (with API only writing a startup marker that the script immediately overwrites) would eliminate cross-writer races.

- `B4` (NAIP/Sentinel writing to wrong state file) means per-type isolation is broken. The whole `_state_file_for_type` abstraction is a lie for any pipeline that inherits `update_progress` from `acquire_imagery.py`. A pipeline type's state file path must be plumbed through to the script, not hardcoded.
