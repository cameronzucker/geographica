# Geographica Companion — Data Ingestion Utility

**Date:** 2026-04-15
**Scope:** Cross-platform (Windows/Linux) desktop tool for downloading and processing all Geographica data pipelines on a fast workstation, then transferring results to a Pi via SCP.

## Problem

Processing imagery on the Pi 5 is slow — NOAA NAIP takes ~6 min/tile for download+reproject+convert, and gdaladdo took 5+ hours for 259K tiles. For serious deployments covering multiple large regions, this means weeks of continuous processing. A workstation with more cores, faster disk, and better network can do this 10-50x faster.

The Pi must remain fully capable of running all pipelines natively. The companion is an optional "fast path" for bulk data preparation.

## Architecture

### Overview

```
WORKSTATION                              PI 5
┌──────────────────────────┐            ┌──────────────────────┐
│ Companion Tool           │            │ Geographica Stack    │
│                          │   SCP      │                      │
│ Browser UI (localhost)   │ ────────── │ /srv/geographica/    │
│ Python backend (FastAPI) │  MBTiles   │   data/*.mbtiles     │
│ Bundled GDAL binaries    │            │                      │
│ Pipeline scripts         │            │ deploy.sh registers  │
│                          │            │ in TileServer config │
└──────────────────────────┘            └──────────────────────┘
```

### Components

**1. Python Backend (FastAPI)**
- Runs on `localhost:9000`
- Reuses the existing pipeline code from `scripts/`:
  - `acquire_imagery.py` — all 5 imagery modes (direct, m2m, nationalmap, noaa, import)
  - `download_elevation.py` — elevation tiles
  - `acquire_naip.py` — NAIP county mosaics (when USDA gateway returns)
- Pipeline orchestration: start, cancel, progress polling
- SCP transfer via `paramiko` (Python SSH library)
- Estimate endpoints (tile count, download size, ETA)

**2. Browser UI**
- Opens automatically at `localhost:9000` on launch
- Mirrors the admin panel's Pipelines tab design:
  - Minimap with bbox drawing (MapLibre GL JS)
  - Source cards with per-source configuration (same card grid layout)
  - Progress bars with cancel support
  - Estimate buttons per source
- Additional "Transfer" tab:
  - Pi hostname/IP input
  - SSH username + password or key file
  - "Test Connection" button
  - File list showing what will be transferred (MBTiles with sizes)
  - "Transfer" button with per-file progress
  - Manual SCP command display as fallback

**3. Bundled GDAL Binaries**
- Pre-compiled GDAL tools (`gdalwarp`, `gdal_translate`, `gdaladdo`, `gdalbuildvrt`, `ogr2ogr`) bundled per platform:
  - `bin/linux-x64/` — from Ubuntu/Debian GDAL packages
  - `bin/windows-x64/` — from OSGeo4W or GISInternals builds
- Companion checks for bundled GDAL first, falls back to system PATH
- Version pinned to match what the Pi uses (GDAL 3.x)

**4. Output**
- MBTiles files written to a configurable output directory (default: `./geographica-data/`)
- `deploy.sh` script generated alongside the data:
  ```bash
  #!/bin/bash
  # Generated by Geographica Companion
  # Run on the Pi after SCP transfer
  DATA_DIR="/srv/geographica/data"
  for f in *.mbtiles; do
    cp "$f" "$DATA_DIR/"
    python3 /path/to/tileserver_config.py add "$DATA_DIR/$f"
  done
  docker compose restart tileserver
  ```

## Pipeline Reuse Strategy

The existing pipeline scripts (`scripts/acquire_imagery.py`, etc.) are designed to run inside Docker containers on the Pi. The companion reuses them with minimal changes:

### What stays the same
- All download logic (HTTP fetching, retry, checkpointing)
- All GDAL conversion commands (gdalwarp, gdal_translate, gdaladdo)
- MBTiles merge logic (SQLite ATTACH + INSERT OR REPLACE)
- Tile index parsing (NOAA shapefile extraction)
- Estimate calculations

### What changes
- **GDAL binary path:** Instead of system GDAL, use bundled binaries from `bin/{platform}/`
- **Output directory:** Configurable, not hardcoded to `/data/`
- **Progress reporting:** Write to a JSON file polled by the FastAPI backend (same pattern as the Pi's pipeline status)
- **No Docker:** Scripts run as direct Python subprocesses, not in containers
- **No TileServer config:** The companion doesn't run TileServer. Config updates happen on the Pi via deploy.sh
- **Concurrency:** Can use more concurrent downloads and GDAL threads (workstation has more resources)

### Import mechanism
The scripts are imported as modules or invoked as subprocesses. The companion's backend wraps them with:
- Working directory management (output paths)
- GDAL binary path injection (PATH or GDAL env vars)
- Progress file reading
- Cancel signal forwarding

## Transfer Flow

### Built-in SCP (primary)

```
1. User enters Pi hostname, username, password/key
2. "Test Connection" verifies SSH access + checks /srv/geographica/data/ exists
3. User clicks "Transfer"
4. For each MBTiles file:
   a. SCP file to Pi:/srv/geographica/data/
   b. Show per-file progress (bytes transferred / total)
5. After all files transferred:
   a. SSH exec: register each source in TileServer config
   b. SSH exec: docker compose restart tileserver
6. Show completion summary
```

Uses `paramiko` for SSH/SCP — pure Python, no external SSH client needed. Supports password and key-file authentication.

### Manual fallback

The UI displays a copyable SCP command:
```
scp ./geographica-data/*.mbtiles user@pi-hostname:/srv/geographica/data/
```

And a deploy command to run on the Pi:
```
ssh user@pi-hostname 'cd /srv/geographica/data && bash deploy.sh'
```

### Prerequisites
- Python 3.10+ (pre-installed on most Linux; downloadable for Windows)
- No Docker required
- No GDAL install required (bundled)
- ~100 MB download (mostly GDAL binaries)

### First run
```bash
# Linux
./companion.sh

# Windows (double-click companion.bat, or:)
python companion.py
```

The launcher:
1. Creates a Python venv if needed
2. Installs pip dependencies
3. Checks for bundled GDAL binaries
4. Starts the FastAPI server on port 9000
5. Opens the default browser to `http://localhost:9000`

## UI Design

### Tabs

**1. Configure**
- Minimap with bbox drawing (same as admin panel)
- Bbox text input (editable, syncs with map)

## Differences from Pi Admin Panel

| Aspect | Pi Admin Panel | Companion |
|--------|---------------|-----------|
| Runs on | Pi (in Docker) | Workstation (native Python) |
| GDAL | In pipeline container | Bundled binaries |
| Output | Direct to /srv/geographica/data/ | Local directory |
| TileServer | Updates config + restart | Generates deploy.sh |
| Transfer | N/A | Built-in SCP + manual |
| Concurrency | 3 (Pi limited) | Up to 16 (workstation) |
| gdaladdo | Hours (4 ARM cores) | Minutes (8-16 x86 cores) |
| Credentials | System keyring (GNOME) | Local config file or OS keyring |

## Credential Storage

On the workstation, credentials are stored via Python's `keyring` library which uses:
- **Windows:** Windows Credential Manager
- **Linux:** SecretService (GNOME Keyring / KWallet)
- **Fallback:** Encrypted file in `~/.geographica-companion/`

The companion does NOT share credentials with the Pi's keyring agent. Users enter credentials separately on the companion.

## What This Does NOT Include

- Running any Geographica services (no TileServer, Valhalla, Nominatim)
- Vector basemap generation (Planetiler requires separate setup)
- POI index building (requires the OSM PBF, done on Pi)
- Valhalla routing data (built from OSM PBF on Pi)
- Nominatim geocoding data (imported from OSM PBF on Pi)
- Any UI for viewing/navigating maps (the companion only produces data)
